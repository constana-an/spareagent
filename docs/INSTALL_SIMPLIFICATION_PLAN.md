# 安装与接入简化计划

日期：2026-10-21（America/New_York）

状态：第一、二、三阶段已完成代码、相关测试和本机更新；第四阶段改用免费本机编译安装，正式签名与公证保留为可选；第五阶段已完成现有 Mac 的维护入口及本机验证。当前分享暂停，无运行任务。

## 目标与范围

提供者首次使用：打开 SpareAgent.app → 完成必要的账号登录和分享确认 → 上线 → 复制邀请链接。后续使用：打开 App → 上线。成员完成一次私网接入后：打开邀请链接 → 同意加入 → 提交任务。

本轮保留现有协调服务、Worker 和浏览器控制页。先解决首次使用和日常启动，再处理运营者部署。按里程碑验收，不将本机验证写成另一台 Mac 的安装验收。

## 第一阶段：修好首次使用中的阻碍

涉及 `packages/worker/app.py`、`app_ui.py`、设备注册及相关测试。

- 分离用户看到的设备名称和注册时的技术标识。显示名允许中文、空格；注册标识满足现有约束，不放宽所有使用 SafeName 的接口。
- 修复设备名称编辑状态影响其他设置加载的问题。用户编辑某一组字段时，其他区域仍能正常刷新。
- 首次页面突出登录、分享范围、额度使用和上线操作；网络选择、设备名称、任务种类、并发和成员上限按需展开。订阅类型保留明确选择或确认，不能靠界面猜测。
- 用简短摘要呈现自动批准、额度消耗和联网权限，详细说明仍可阅读，默认值与实际行为一致。首次消耗额度前明确告知自检，不能用隐藏确认代替本人同意。
- 已完成的安装、注册和自检可复用，失败重试从可恢复的步骤继续。

验收：中文及带空格名称能完成模拟注册；首次失败后重试不会重复建组；编辑名称不再让设置空白；普通启动和无推理连接检查不消耗额度。

## 第二阶段：用正常的 Mac App 启动

新增轻量 Swift/AppKit 启动器和构建入口，复用现有 Python Worker、运行环境安装逻辑及本地控制页。先用浏览器展示完整控制页，App 负责进程、进度、状态和退出。

- 分 CPU 打包所需 Python 运行环境与 Worker 依赖，用户无需 Homebrew、Node、Python 或终端。Codex 继续复用现有固定版本下载和校验逻辑；构建时评估是否随包提供。
- 首次安装在 App 内显示进度、失败原因和重试入口；运行文件放在稳定目录，更新不能删除已有注册信息。
- 菜单栏显示离线、准备中、在线或连接异常，并提供“打开控制页”“暂停分享”“退出”。重复打开只显示已有实例。
- 关闭控制页后，菜单栏仍明确显示运行状态。退出时复用已有的“运行完再下线 / 立即停止并交还”处理，不留下无提示的接单进程。
- 打开 App 默认不自动上线；登录启动、自动更新延后处理。

验收：Finder 双击可打开；不出现终端；重复启动不产生第二个 Worker；安装失败可重试；退出后停止接单；升级保留已有身份和配置。未签名的测试包仍如实说明 macOS 首次放行要求。

## 第三阶段：省掉手动证书操作

优先验证现有 Tailscale 私网下的 Serve HTTPS，使用完整的 `*.ts.net` 主机名。官方说明支持私网服务转发与 HTTPS；这一步不要求先购买域名。[Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve)、[HTTPS 证书](https://tailscale.com/docs/how-to/set-up-https-certificates)

- 先只读检查当前 Serve/Funnel、端口和 HTTPS 配置；选择不冲突的入口，保留现有应用的入口和可回退配置。
- 同步调整浏览器入口、Worker API 地址、允许的 Origin、代理配置和打包配置，分别验证登录、上传、状态更新和下载。
- 正常页面默认自动连接；失败时区分“Tailscale 未连接”“服务不可达”“证书或地址不匹配”，并给出对应动作。
- 验证新地址后，简化成员指南，移除正常流程中的证书导入和 curl 检查步骤。
- 首次启用 HTTPS 可能需要 tailnet 管理员操作，并会将证书主机名记录到公开的证书透明度日志；配置前先确认名称适合公开。服务访问范围仍由私网控制。

验收：新地址在未手动信任私有 CA 的浏览器环境中通过 TLS 校验；Worker 同样正常校验 TLS；成员完成一次私网接入后可凭邀请链接使用。跨设备连通性留待另一台设备验证。

这一步不会省掉 Tailscale 安装和登录。若将来要求成员完全不装 Tailscale，需另定公网 HTTPS 接入方案，单独评估部署位置和访问范围。

## 第四阶段：免费本机安装，签名与公证保留为可选

用户选择免费本机编译路线：运营者提供包含 Swift 源码和固定运行环境的私有安装包，提供者首次运行安装脚本，在自己的 Mac 上生成菜单栏 App，以后双击启动。缺少 Apple 命令行工具时先完成 Apple 的安装，再重试。此路线不提交 Apple 公证，不承诺所有系统都没有额外提示。安装与更新保留原有设备身份和分享设置，不自动上线。说明见 [LOCAL_APP_INSTALL.md](LOCAL_APP_INSTALL.md)。

以后准备正式分发时，可继续使用以下付费签名与公证流程。App 流程稳定后，为实际分发包完成 Developer ID 签名、公证和票据装订，并核对包内可执行组件。[Apple Developer ID](https://developer.apple.com/developer-id/)、[分发打包说明](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution)

依赖可用的 Apple Developer 团队、证书及签名权限。没有这些条件时，仍可交付本机测试包，但不能宣称已经解决首次安全放行。

验收：从实际下载渠道获取带隔离属性的包，在干净环境下验证首次打开、安装、登录与退出。普通的“从互联网下载”确认与未识别开发者拦截分别记录。

## 第五阶段：简化运营者维护

在提供者和成员流程稳定后，再整合现有部署与打包脚本：检查运行条件 → 生成或读取配置 → 检查地址 → 启动服务并检查健康 → 生成私有安装包。

现有安装走升级或恢复路径，保留数据和邀请配置；真实执行仍是明确开启的选项，不能因为重新部署而自动启用。范围先限于当前 Mac 私有部署。

验收：同一入口重复执行不重建已有身份、不清空数据；失败能定位到具体步骤；重启后原有成员和文件可用。

## 现阶段验证安排

- 这台 Mac 可以完成 App 构建、隔离状态目录中的模拟首次启动、下载失败重试、重复启动、暂停与退出，以及浏览器 TLS 和接口验证。
- 使用新的本地系统用户可补测用户级依赖缺失，但仍不等于全新 Mac。只验证本机 CPU；另一架构不能仅凭生成安装包标为已通过。
